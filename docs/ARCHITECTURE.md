# EduGen Architecture — FYP-2

This document explains **why** the system is built this way. Much of it maps
directly onto chapters of the final report.

---

## 1. What changed from FYP-1, and why

| Area | FYP-1 | FYP-2 | Why it had to change |
|---|---|---|---|
| Content source | 120 hand-written MCQs and static lesson text | Everything generated by the Concept Clarifier Agent, grounded in RAG | A fixed bank cannot adapt; the project's premise is dynamic content |
| Quiz grading | Graded against the static bank | Generated quiz stored in `quiz_sessions`, graded server-side | **FYP-1 could not grade a generated quiz at all** — the questions were never persisted |
| Analysis | `accuracy < 50%` per topic | Recency-weighted mastery, trend, response time, distractor analysis, prerequisite root cause | Topic-level accuracy throws away most of the evidence the database already holds |
| Recommendation | Pick the weakest topic | A 6-rule policy engine that also emits a retrieval brief | The Concept Clarifier needed a precise instruction, not a topic name |
| Identity | `student_id` sent by the browser | Signed server-side session | Changing a number in the URL exposed another student's history |
| Interface | One 2,100-line single-page template | 12 server-rendered pages | Each screen is now linkable, demonstrable and independently testable |
| Knowledge | none | File-backed hybrid vector index | Ungrounded LLM output cannot be cited or verified |

## 2. The concept model

`core/concepts.py` is the single source of truth: 44 concept tags grouped into
8 modules, each with a summary, retrieval keywords, and **prerequisite edges**.

```
class-definition
   ├── object-instantiation ──► this-keyword
   │                        └── reference-semantics ──► null-pointer-exception
   ├── inheritance-basics ──► method-overriding ──► dynamic-method-dispatch
   │                                                  └── runtime-polymorphism
   └── access-modifiers ──► data-hiding ──► getters-setters ──► defensive-copying
                                                                  └── immutability
```

The graph is what turns "you are weak at method overriding" into "you are weak
at method overriding **because** inheritance basics is not solid". That is the
main pedagogical contribution of FYP-2.

`LEARNING_ORDER` is a topological sort of the graph, used by rule R6 to pick
the next unseen concept in a teaching-safe order.

## 3. Agent contracts

Each agent has one responsibility and a documented input/output shape, so any
one of them can be replaced without touching the others.

### Coordinator — `agents/coordinator_agent.py`
Pure control flow. No pedagogy, no analysis, no LLM calls.

- First visit (no quiz history) → straight to Concept Clarifier at the entry concept
- Returning student → Performance Analysis → Adaptive Content → Concept Clarifier

Every stage appends to a `trace` list, which `/pipeline` renders.

### Performance Analysis — `agents/performance_analysis_agent.py`
Measures what the student knows. Deliberately does **not** decide what to do
about it.

Signals used:

1. **Per-concept accuracy** — raw correct/total
2. **Mastery (EWMA, α = 0.45)** — recent answers weighted higher, so improvement
   shows up immediately instead of being buried under early mistakes
3. **Trend** — first half vs second half of the attempt history
4. **Response time** — correct-but-slow is flagged `fragile`
5. **Distractor analysis** — a wrong option chosen twice or more is a named
   misconception, not random error
6. **Prerequisite root cause** — walks the graph to find the real gap
7. **Review decay** — mastered concepts go stale after 7 days

Thresholds live in constants at the top of the file, so the evaluation chapter
can report a sensitivity analysis by changing them.

### Adaptive Content — `agents/adaptive_content_agent.py`
A deterministic policy engine. Six rules, checked in order, first match wins:

| Rule | Condition | Action |
|---|---|---|
| R1 | No quiz history | `first_lesson` at the entry concept, Easy |
| R2 | A weak concept has a weak prerequisite | `remediate_prerequisite` |
| R3 | A weak concept with sound prerequisites | `revisit`, difficulty scaled by mastery and trend |
| R4 | A mastered concept has gone stale | `review` at one level up |
| R5 | Moderate concepts remain | `reinforce` the weakest |
| R6 | Everything strong | `advance` to the next unseen concept |

Determinism is the point: every recommendation is reproducible and explainable,
which is what makes it defensible in a viva. `scripts/test_adaptivity.py`
asserts that each rule fires in its scenario.

Within R2, causes are ranked so a **measured** weak prerequisite outranks one
that was merely never assessed — otherwise a single untested foundational
concept would hijack every recommendation.

### Concept Clarifier — `agents/concept_clarifier_agent.py`
The only agent allowed to call an LLM.

```
retrieval brief → RAG retrieve → prompt assembly → LLM (2 models)
                → JSON validation → fallback ladder
```

Fallbacks, in order:
- Lesson: LLM+RAG → LLM → the local concept note for that tag
- Quiz: LLM+RAG → LLM → an explicit "unavailable" response

There is deliberately **no** static question bank fallback. Serving stale
hand-written questions while claiming they were generated would misrepresent
the system during evaluation.

## 4. The retrieval brief

This object is what makes the pipeline agentic rather than a chain of function
calls. The Adaptive Content Agent — which owns pedagogy — decides what should be
looked up, and hands the Concept Clarifier a precise instruction:

```json
{
  "concept": "constructor-chaining",
  "difficulty": "Medium",
  "mode": "lesson",
  "query": "Constructor Chaining this() super() delegate chaining first statement",
  "concept_tags": ["constructor-chaining", "constructor-overloading", "super-keyword"],
  "focus_notes": [
    "The student repeatedly chose: \"super() can be second\" - correct that directly."
  ],
  "top_k": 6,
  "issued_by": "Adaptive Content Agent",
  "rule": "R3"
}
```

`focus_notes` carries this student's actual recorded misconceptions into the
prompt, which is how the generated content becomes personal rather than
generic. When remediating a prerequisite, the **symptom's** misconceptions
travel with the brief too.

## 5. RAG design

### Why not Chroma / FAISS / a vector database
The corpus is a few thousand chunks. A file-backed NumPy matrix searches it in
under a millisecond, adds no service to deploy, and can be inspected, versioned
and handed to an examiner. `data/rag_index/` is three readable files.

### Hybrid ranking
```
score = 0.62 · cosine + 0.26 · lexical + 0.12 · concept-tag match
```

Pure cosine on a small academic corpus returns "related-sounding" text. The
lexical term keeps exact Java vocabulary (`super()`, `@Override`, `finally`)
anchored, and the tag term keeps results inside the concept the agent asked
about. Each component is reported separately in the UI so the weighting can be
justified.

### Chunking
Split on Markdown headings first (semantic boundaries), then pack to ~900
characters with 150 characters of overlap, never cutting a sentence if it can
be avoided. Every chunk is tagged against the 44 concepts by keyword matching,
plus any explicit front-matter tag.

### Embedding backends
Three, behind one interface:

| Backend | When |
|---|---|
| `sentence-transformers` | Recommended. MiniLM-L6-v2, ~90 MB, runs on Apple Silicon MPS |
| `ollama` | If Ollama is already installed, e.g. `nomic-embed-text` |
| `hashing` | Zero dependencies. Lower quality but the system always boots |

The index records which backend built it and warns loudly on mismatch.

## 6. Security

- Student identity comes from a signed server-side session, never the request
- `@login_required` on pages, `@api_login_required` on JSON endpoints
- No endpoint accepts a `student_id` parameter
- Passwords hashed with werkzeug PBKDF2
- Correct quiz answers stay in `quiz_sessions` until submission
- `HttpOnly` and `SameSite=Lax` session cookies

`scripts/smoke_test.py` asserts that a second account sees zero records from
the first.

## 7. Database

```
users(id, name, email UNIQUE, password_hash, created_at)
students(id, name, user_id → users.id UNIQUE, created_at)
quiz_results(id, student_id, topic, concept, difficulty, score,
             total_questions, attempt_number, source, duration_ms, timestamp)
question_attempts(id, quiz_result_id, question_index, concept_tags,
                  is_correct, student_answer, correct_answer,
                  time_taken_ms, question_text, chosen_option_text)
quiz_sessions(id, student_id, concept, topic, difficulty, source,
              payload_json, consumed, created_at)
recommendations(id, student_id, focus_concept, difficulty, action, reasoning,
                accepted, final_concept, final_difficulty, created_at)
lesson_views(id, student_id, concept, difficulty, source, viewed_at)
```

`init_db()` runs forward migrations with `ALTER TABLE`, so an existing FYP-1
`data/edugen.db` keeps working — copy it in and it will be upgraded in place.

`recommendations.accepted` is what makes "how often did students trust the
agent?" a measurable result rather than an anecdote.

## 8. Evaluation angles this design supports

1. **Adaptive accuracy** — do the rules fire correctly? `test_adaptivity.py`
   already demonstrates all six.
2. **Grounding quality** — what fraction of generated lessons cite at least one
   retrieved passage? `generated_by` records `llm+rag` vs `llm` on every item.
3. **Retrieval quality** — the three score components are exposed per result on
   `/library`, so precision at k can be measured per concept.
4. **Student agency** — acceptance rate from `recommendations`, already on `/history`.
5. **Root-cause value** — compare mastery gain when R2 fires (teach the
   prerequisite) against R3 (repeat the symptom).
6. **Responsiveness** — `elapsed_ms` on every pipeline run, shown on `/pipeline`.
